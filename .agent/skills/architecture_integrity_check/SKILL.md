# 目的
このスキルは、Astroプロジェクトにおいて「どこに何があるか」「どこを変更すればよいか」という**透明性 (Transparency)** と **変更容易性 (Maintainability)** が維持されているかを定期的に監査するために使用します。ディレクトリのルール違反や、肥大化したコンポーネント（Fat Component）を検出し、健康なコードベースアーキテクチャを保つことを目的とします。

# 実行手順と評価軸

## 1. ディレクトリとファイルの責務検証 (Directory Responsibilities)
コードベース（主に `src/` 配下）を解析し、各ファイルが役割に合った場所に配置・実装されているかを確認します。
- **ページの役割 (`src/pages/`)**: ルーティングと組み上げの「ハブ」に徹しているか。このディレクトリ内のファイルに、具体的なUIパーツのマークアップや複雑な状態管理が直接記述されていないか（ページコンポーネントの肥大化チェック）。
- **コンポーネントの粒度 (`src/components/`)**: 再利用可能なUIが配置されているか。さらに、汎用UI（`ui/`）、ドメイン特化（`domain/`）、レイアウト（`layout/`）など、責務に応じた整理が維持されているか。
- **純粋な関数の分離 (`src/utils/`, `src/lib/`)**: コンポーネントやページに依存しないデータ加工、API通信、バリデーションロジックが、UIから切り離されて配置されているか。

## 2. ロジックとデータフェッチングの分離 (Separation of Concerns)
Astroコンポーネントの構造（特にフロントマター部分）がルールに従っているかを評価します。
- **フロントマターのシンプルさ**: `.astro` ファイル上部のスクリプト部分（`---`）に、数百行に及ぶような複雑なビジネスロジックやデータの再構築処理が直書きされていないか。「取得 (Fetch)」と「準備 (Map)」に留まっているか。
- **状態管理の境界**: ReactなどのUIフレームワーク層において、状態（State）を持つべきでない静的なコンポーネントが作成されていないか。逆にAstro層で扱うべき処理がReact側に漏れ出していないか（アイランドアーキテクチャの適正利用）。

## 3. インポートパスの正規化 (Path Alias Rules)
ファイル間の依存関係（インポート）が変更に強い形になっているかを確認します。
- **相対パスの排除**: コンポーネント階層の深い場所からのインポートで `../../../../components/Button.astro` のような「壊れやすい」相対参照が使用されていないか。
- **エイリアスへの強制**: `tsconfig.json` に定義されたパスエイリアス（例: `@/components/...` や `@/utils/...`）を用いたインポートに統一されているか。

## 4. ドキュメンテーションと「Why」の記述 (Documentation Rules)
将来のメンテナンスを見据えたコメントが残されているかをチェックします。
- **「Why」の有無**: 複雑なワークアラウンド、ハック的なアプローチ、または特定の制約による実装に対して、「なぜこの方法を採用したのか（Why）」を説明するコメントが存在するか。
- **不透明なコード**: 意図が不明瞭な「マジックナンバー」や、何をしているかしか書かれていない無意味なコメントがないか。

# レポートの生成と改善案の提示
調査が完了したら、アーティファクト（Markdown形式など）を使用して、レビュー結果を報告します。
報告時には以下の項目を含めてください。

### レポートの構成案
1. **アーキテクチャ健康診断サマリー**: ディレクトリの責務違反や密結合度合いに基づく全体評価。
2. **責務を逸脱したファイルリスト**: 本来 `src/components/` や `src/utils/` にあるべきコードが `src/pages/` に書かれているなどの違反箇所と、その理由。
3. **リファクタリングの提案**: 肥大化したコンポーネントの分割案や、共通ロジックの抽出（`utils`化）に向けた具体的なファイル分割構成案。
4. **インポートパスの修正パス**: エイリアスを使用していないファイルのリストと、変更すべきパスの対応表。
5. **Next Action**: 優先的にファイルの移動・分割を行うべきタスクのリスト。

# 留意事項
- 問題を指摘する際は、単に「ルール違反です」と伝えるだけでなく、「どのようにファイルを分割・移動すればアーキテクチャがきれいになるか」という**リファクタリングの道筋**を明確に示すこと。
- パスの書き換えやファイルの移動の提案は、実行前にユーザーの承認を得ることを推奨すること。
