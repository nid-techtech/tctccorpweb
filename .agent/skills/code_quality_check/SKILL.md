# 目的
このスキルは、Astroプロジェクト（またはその他のウェブプロジェクト）において、セキュリティの脆弱性、パフォーマンスのボトルネック、不必要な冗長性、コードの重複を検出し、コードベースの品質（変更容易性と透明性）を高く保つための静的解析・レビューを実行します。

# 実行手順

## 1. 分析の準備とターゲットの特定
- ユーザーが指定したファイル、ディレクトリ、またはプロジェクト全体を対象とします。
- 必要に応じて `list_dir` や `grep_search` を使用してプロジェクトの構造を把握し、主要な実装箇所（`src/pages/`, `src/components/`, `src/utils/` など）を特定します。
- `package.json` などの設定ファイルを読み込み、依存関係を確認します。

## 2. セキュリティと脆弱性のチェック
コードを読み取り、以下のセキュリティリスクが潜んでいないか確認します。
- **XSS（クロスサイトスクリプティング）**: ユーザー入力や外部データを適切にサニタイズせずに画面に出力している箇所（例：Reactの `dangerouslySetInnerHTML`、Astroの `set:html`、Vanilla JSの `innerHTML`）の有無。
- **クレデンシャルのハードコード**: APIキー、アクセストークン、パスワードなどがソースコード内に直接書き込まれていないか（`.env` などの環境変数に分離されているか）。
- **依存パッケージの脆弱性**: ターミナルで `npm audit` を実行し、既知の脆弱性を持つパッケージが含まれていないか確認します。
- **インジェクション**: データベースクエリやAPIのリクエスト構築に渡すパラメータが安全に処理されているか。

## 3. パフォーマンスの最適化チェック
ウェブサイトのパフォーマンス（読み込み速度、レンダリング速度）に悪影響を与える実装がないか確認します。
- **メディアの最適化**: 画像（`<img>`）に対して適切な遅延読み込み (`loading="lazy"`) やレスポンシブなサイズ指定が行われているか、あるいはAstroの `<Image>` / `<Picture>` コンポーネントが使用されているか。
- **JavaScriptのロード制御**: Astroアイランド (`client:load`, `client:visible`, `client:idle` 等) が必要最小限に抑えられているか。静的な表示のみのコンポーネントにJSがロードされていないか。
- **不要な再レンダリングとループ処理**: クライアントサイドのフレームワーク（React等）で、無駄な状態更新や重い同期ループ処理が行われていないか。
- **バンドルとインポートの肥大化**: サードパーティライブラリ全体をインポートしていないか。必要なモジュールのみをインポート（Tree Shakingを意識した実装）しているか。

## 4. 冗長性とコードの重複のチェック (DRY原則・変更容易性)
コードベースが「Astroプロジェクトのルール」に従って整理されているかを評価します。
- **コンポーネントの重複**: 視覚的・機能的に類似した複数のコンポーネントが存在しないか。これらを1つの汎用コンポーネント（Propsで表示を制御）に結合してリファクタリングできないかの検討。
- **スタイルの重複**: Tailwind CSSのユーティリティクラスやCSSの記述で、同じスタイリングの組み合わせが散在していないか。必要に応じて共通クラス化やデザインシステム定義（`tailwind.config.mjs` 等）を提案します。
- **ロジックの重複**: APIからのデータ取得やデータのフォーマット、バリデーション処理などのビジネスロジックが各コンポーネント内に重複していないか。これらが `src/utils/` や `src/lib/` に関数として切り出されているかを確認します。
- **無用な抽象化と冗長なコード**: 逆に細かく分けすぎて可読性を下げていたり、使用されていない使途不明な関数や変数（デッドコード）がないか。

## 5. レポートの生成と改善案の提示
調査が完了したら、アーティファクト（Markdown形式など）を使用して、ユーザーにレビュー結果を報告します。
報告時には以下の項目を含めてください。

### レポートの構成案
1. **総評サマリー**: 今回のチェックで判明したコードの健康状態。
2. **セキュリティの課題と対策**: 発見された脆弱性と、具体的な修正コードの提示。
3. **パフォーマンスの課題と対策**: レンダリングや読み込み速度を改善するための修正案。
4. **DRY原則違反とリファクタリング案**: コピペコードや類似部分の統合案、ユーティリティ化の提案。
5. **次のアクションリスト**: ユーザーがすぐに取り掛かれるように優先順位をつけたタスクリスト。

# 留意事項
- 問題を指摘するだけでなく、「どう修正すればよいか（コード例）」を必ずセットで提示すること。
- 自動ファイル修正を行う前に、修正の規模が大きい場合はユーザーと同意・確認を取ること。
- 修正に伴い既存の機能が破損しないよう、安全性を保ったままのコード提案を心がけること。
