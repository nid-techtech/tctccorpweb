# Astro プロジェクト開発・管理原則

本ドキュメントは、Astroを用いたウェブサイト制作において、**変更容易性 (Maintainability/Modifiability)**、**透明性 (Transparency)**、**DRY (Don't Repeat Yourself) 原則**を順守するための設計およびコーディングルールを定義します。

## 1. ディレクトリ構成とファイルの責務（透明性の確保）
各ディレクトリとファイルの役割を厳格に分離し、「どこに何があるか」「どこを変更すればよいか」を常に明確にします。

- **`src/pages/`**:
  - ルーティングとページ全体の組み上げ専用とします。
  - 具体的なUIや複雑なロジックを直接記述せず、コンポーネントを組み合わせる「ハブ」に徹することで、ページ構造の透明性を保ちます。
- **`src/components/`**:
  - ページを構成する再利用可能な要素を配置します（DRY原則）。
  - さらに責務に応じて `ui/` (汎用ボタンなど), `domain/` (事業ロジックに縛られた表示), `layout/` (ヘッダーや特定の枠組み) といったサブディレクトリに分割し、影響範囲を限定します。
- **`src/layouts/`**:
  - 全ページまたは特定カテゴリのページで共通する構造（`<html>`, `<head>`, ナビゲーション、フッターを含む）を定義します。
- **`src/utils/` / `src/lib/`**:
  - データ加工・API通信・共通のバリデーションなど、UIに依存しない純粋な関数を集約し、コンポーネント間の重複したロジックを排除します（DRY原則）。
- **`src/content/`**:
  - Content Collectionsを利用し、MarkdownやMDXベースのコンテンツとそのスキーマ定義を集中管理します。インテグレーションの透明性を高めます。

## 2. コンポーネント設計（DRY原則と変更容易性）

- **単一責任の原則 (Single Responsibility Principle)**:
  - 1つのコンポーネントは1つの機能、または1つのUIの振る舞いに専念させます。巨大なコンポーネントは避け、適切な粒度に分割してください。
- **Astro層とUIフレームワーク層の明確な分離**:
  - 静的・装飾的なUIはAstroコンポーネント(`.astro`)、状態管理やブラウザ側での複雑なインタラクションが必要な部分はReact等のUIフレームワークで作成し、Astroのアイランドアーキテクチャ (`client:*` ディレクティブ) を適切に使い分けます。
- **Propsの型定義（透明性）**:
  - TypeScriptを利用し、コンポーネントが受け取る `Props` を `interface` または `type` で必ず明記します。これによりデータの流れが追いやすくなり、変更時のエラーを未然に防ぎます。

## 3. スタイリング（変更容易性と局所性）

- **スコープ付きCSSの活用**:
  - Astroの `<style>` ブロックによるスコープ付きCSSを標準とし、グローバルな副作用を排除します（変更容易性）。
- **デザインシステムの共通化（DRY原則）**:
  - カラーパレット、タイポグラフィ、スペーシングなどのデザイン変数は、CSSカスタムプロパティ（CSS Variables）やTailwind CSSの設定（`tailwind.config.mjs`）で一元管理します。コンポーネント内にマジックナンバー（直接の数値やカラーコード）をハードコードしないこと。

## 4. ロジックとデータフェッチング（透明性）

- **フロントマター (Frontmatter) の責務**:
  - `.astro` ファイルの上部（`---` で囲まれたスクリプト部分）は、必要なデータの「取得(Fetch)」と、テンプレートへ渡す「データの準備(Map)」のみに限定します。
  - 複雑なビジネスロジックはフロントマターに書かず、`src/utils/` などから関数としてインポートしてください。
- **パスエイリアス (Path Alias) の強制（変更容易性）**:
  - 特有の階層から相対パス (`../../components/Button.astro` など) を使うことを避け、`tsconfig.json` に設定したエイリアス（例: `@/components/Button.astro`）を使用します。これにより、ディレクトリ移動時の参照調整が不要になり変更容易性が向上します。

## 5. コメントとドキュメンテーション（透明性）

- **「Why」を残す**:
  - コードを読むだけで「何をしているか（What）」は伝わるように記述し、コメントには設計背景や「なぜそのような実装にしたのか（Why/制約事項）」を記述します。
  - ハック的アプローチや複雑なワークアラウンドを採用した場合は、将来の自分が変更しやすいように必ず根拠を併記してください。

---
このルールドキュメントは、チームでの一貫した開発体験を維持しつつ、システムが成長（コンテンツ、ページの増減、コンポーネントの入れ替えなど）しても安全にスケールボードを保つための基盤となります。
